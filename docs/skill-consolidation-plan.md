# ClankerKit Skill Consolidation Plan

## Objective

Reduce skill sprawl by consolidating overlapping workflows into a smaller set of high-leverage, repo-agnostic skills with deterministic contracts.

## Core skill set

1. `truth-recovery-program`
2. `deterministic-execution-lane`
3. `merge-train-governor`
4. `evidence-research-flywheel`
5. `orchestrator-hardening`

## Consolidation map

## `truth-recovery-program`

Consolidates:

- merged-history quality auditing
- intent-versus-implementation drift analysis
- queue rebaseline and closure decisions
- evidence-first governance verdicts

## `deterministic-execution-lane`

Consolidates:

- resumable checkpoint loops
- strict phase contracts
- fail-closed execution state handling

## `merge-train-governor`

Consolidates:

- queue triage and lane selection
- pre-merge validator and readiness gates
- review hygiene and controlled promotion checks

## `evidence-research-flywheel`

Consolidates:

- evidence intake and normalization
- confidence-scored research synthesis
- bounded planning handoff for implementation

## `orchestrator-hardening`

Consolidates:

- orchestration contract bootstrapping
- lane routing and escalation policy definition
- continuation authority and stop-boundary hardening

## Parameterization requirements

Each consolidated skill should externalize:

- tracker nouns (`issue`, `ticket`, `task`, `workpacket`)
- environment names (`local`, `staging`, `preview`, `prod-like`)
- runtime entrypoints (UI, API, CLI, jobs, workers)
- evidence thresholds and classification rules
- branch and release policy constraints
- validator and smoke command contracts

## Assumptions to remove

- project-specific IDs or lane names
- hardcoded repository paths
- product-specific operational vocabulary
- environment variables that do not generalize

## Shared output contract

All consolidated skills should emit:

- deterministic status (`success`, `partial`, `blocked`, `failed`)
- explicit classification output
- artifact paths for evidence
- unverified assumptions
- remediated-now versus deferred split
- owner and tracker references for deferred work

## Rollout sequence

1. publish consolidated skills as `provisional`
2. run old and new workflows in parallel for 2 to 3 cycles
3. compare output quality and remediation outcomes
4. deprecate overlapping workflow variants after parity
5. remove duplicated logic after stability is proven

## Success criteria

- fewer skills with clearer selection boundaries
- no drop in evidence quality or safety posture
- lower operator confusion and lower invocation overhead
- improved portability across repositories
